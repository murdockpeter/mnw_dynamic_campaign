Architecture Intent

Design Rules

The current repo already has the right separation for this work. The goal is to deepen it, not replace it.

  • ui/ stays the single visual frontend surface.
  • electron/ remains a thin wrapper around app-safe desktop APIs.
  • portable/lib/*.mjs continues to own file writes, packaging, ingest, and persistence operations.
  • engine/ and state/* remain the campaign runtime model.
  • shared/campaign-generator.mjs remains the deterministic generator and theater model.
Key principle: new UI controls should not bypass the runtime and write raw files directly unless explicitly operating in a guarded advanced-repair mode.

Feature Plans

Feature 01

Manual Mission-Result Entry

  • Split the current flow into Quick Result and Advanced Result.
  • Quick Result should cover outcome, elapsed time, player damage, key kills, and key ammo expenditure.
  • Advanced Result should allow arbitrary event rows mapped onto runtime ingest events.
  • Add validation before save and a state-delta preview showing what changes in order_of_battle, mission_history, and world_state.
  • Add options for save without advancing time and save + advance X hours.
  • Create a backup of campaign_state.json before each write and preserve append-only mission result history.
UI Work Validation Layer Backup Support
Feature 02

Campaign-State Editor

  • Add a structured editor inside Campaign Tracking for metadata, mission pointer, clock, unit state, world state, and module state.
  • Start with safe structured forms, then optionally expose a guarded Raw JSON tab for advanced repair.
  • Add diff preview before commit and schema normalization on save.
  • Prevent overwrite if the state file changed on disk since the last load.
  • Write a timestamped backup on every commit.
Structured Forms Diff Preview Conflict Checks
Feature 03

Module Enable/Disable Controls

  • Add a module registry so the UI can discover available modules instead of hardcoding them.
  • Expose enable toggles and editable module config fields in Setup or Campaign Tracking.
  • Support both default module settings and campaign-specific overrides.
  • Warn before disabling a module that already has meaningful state on the current campaign.
Registry Config UI Campaign Overrides
Feature 04

DB-Informed Force Selection

  • Add force pools filtered by theater, year, faction, role, and doctrinal availability.
  • Separate theater OOB from mission OOB so the whole theater can feel alive without putting every unit into every scenario.
  • Expose player platform, support pool, enemy pool, and doctrine mode inside authoring.
  • Persist theater-picture state so force availability survives across campaign steps.
  • Use DB-indexed metadata as the source for realistic unit selection and role weighting.
Theater OOB Mission Slice DB Filters
Feature 05

Installer-First Desktop Packaging

  • Make the installer the primary product shape, not just a convenience wrapper.
  • Polish first-launch setup, saved-path validation, and settings migration.
  • Bundle the desktop guide, sample content, debug docs, and a support-bundle export.
  • Expose app versioning and upgrade-safe settings migration.
  • Add a support bundle containing settings, version, workflow state, recent payloads, and redacted logs.
Migrations Support Bundle First-Launch UX
Cross-Cutting

Shared Platform Work

  • Add schema validation for settings, mission-result payloads, campaign state, and module config.
  • Add reusable backup/restore helpers before any high-risk write.
  • Add toasts or notifications for success, validation errors, and irreversible edits.
  • Add a lightweight audit log of operator actions.
  • Add regression checklists for generate, build, deploy, export, ingest, and continue flows.
