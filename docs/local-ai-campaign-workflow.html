Repo Mental Model

MNW Content Layer

  • src/package/ is the editable source tree for the included sample package.
  • src/packages/<campaign-id>/ is where separate standalone campaign packages should live.
  • .mis and .cmp files are the in-game scenario and campaign scripts.
  • .mis.json and .cmp.json are metadata sidecars.
  • tools/build.ps1 turns source content into a valid .kyt package.
  • tools/deploy.ps1 copies the built package into test locations.

Persistence Layer

  • engine/ defines the shared campaign model and runtime.
  • modules/ contains pluggable persistence systems like damage and ammo.
  • campaigns/ contains campaign-state bootstrap/config files.
  • state/ is local runtime state and should stay uncommitted.
  • ui/ is the operator console for state inspection and result drafting.

Validated Guardrails

Important

These are not style preferences. These are rules that were validated by real failures, real rebuilds, real Player.log inspection, and real in-game success. A new operator or AI tool should follow them exactly.

What To Do

  • Treat the selected package source tree as the editable source of MNW package content.
  • Use src/package/ for the included sample package and src/packages/<campaign-id>/ for standalone distributable campaigns.
  • Use the mission namespace that actually exists in the package, such as norwegian_shadow.norwegian_shadow.bear_gap.
  • Add campaign progression one link at a time: prove Mission 1 -> Mission 2, then add Mission 3.
  • Rebuild after every mission or campaign edit.
  • Redeploy after every rebuild and verify the deployed hashes match the file in dist/.
  • Fully exit and relaunch MNW when validating progression or save behavior.
  • Keep a known-good minimal campaign graph available and restore it when debugging.

What Not To Do

  • Do not guess official-style mission IDs such as campaigns.norwegian_shadow.* unless the package truly uses them.
  • Do not assume a campaign bug is a graph problem if the debrief is hanging on Saving....
  • Do not force unrelated campaigns into one shared package if they are supposed to ship independently.
  • Do not trust deployment without hash verification.
  • Do not add several new missions and graph links at once if you have not yet proven the prior progression step.
  • Do not casually use complex mixed formations until save/snapshot behavior has been tested.
Working progression pattern recovered in live testing

1. Restore known-good Mission 1 -> Mission 2 baseline.
2. Prove Mission 1 saves and unlocks Mission 2.
3. Fix any Mission 2 save/snapshot problems.
4. Reintroduce Mission 3 with the smallest graph-only change.
5. Rebuild, redeploy, hash-check, restart the game, and test again.

Package Model

Sample Package

The repo keeps Norwegian Shadow in src/package/ as the included known-good sample package. Building that tree produces dist/norwegian_shadow.kyt.

Standalone Campaign Packages

A campaign that is meant to be its own distributable should live in its own tree under src/packages/<campaign-id>/ and should build to its own archive such as dist/iron_archipelago.kyt.

Important

Do not permanently pack unrelated campaigns into one shared .kyt just because it is convenient for a quick test. If the campaign is supposed to be its own thing, give it its own package, its own manifest, its own locale file, and its own mission namespace.

Simple Three-Scenario Campaign Plan

Recommended beginner structure

Start with one player boat, one clear theater, and one escalation path. The point is not to build the perfect campaign. The point is to prove the loop: author mission, play mission, report result, persist state, generate the next mission.

Mission 1

Initial Intercept

A constrained submarine-vs-submarine patrol. Goal: find and survive, with or without a kill.

Mission 2

Escalated Hunt

The theater thickens. Add supporting ASW aircraft, surface escorts, or shore sensors around the original contact area.

Mission 3

Breakpoint

Final containment or breakout mission. Use previous damage, readiness, and ammo state to shape both sides.

Full Local Workflow

1

Open the repo in your AI tool

Give the AI the working folder and tell it to inspect before editing.
Good first instruction

"Read README.md and RESEARCH.md first. Then inspect src/package/, src/packages/, campaigns/, engine/, modules/, tools/, and ui/.
I want a simple three-scenario dynamic campaign for Modern Naval Warfare. Use the existing repo patterns, keep persistence
modular, decide whether this belongs in the sample package or as its own standalone package tree, add campaign links one
step at a time, and validate any changes with the local build, deploy, hash-check, and test scripts."
2

Create or clone a campaign baseline

The easiest start is to duplicate the sample campaign and rename it.
  • For a variation of the included sample, duplicate files under src/package/.
  • For a fully separate distributable campaign, create a new package tree under src/packages/<campaign-id>/.
  • Rename the campaign ID, mission IDs, sidecars, and visible strings.
  • Create or update the matching persistence bootstrap under campaigns/<campaign-id>/.
  • Keep the first implementation simple and known-good.
  • Do not invent a mission ID prefix. Derive it from the actual package filename and internal folder structure.
3

Author the three scenario arc

This is where the AI should help with order of battle, objective phrasing, and escalation logic.
  • Mission 1 should be survivable and easy to test.
  • Mission 2 should depend on Mission 1 state, even if only through ammo and damage carryover.
  • Mission 3 should be the payoff mission with a cleaner end-state.
  • Ask the AI to keep the map bounds, starting positions, and end conditions conservative at first.
  • Avoid unnecessary complex formations until the campaign saves cleanly after debrief.
4

Build and deploy the package

Do not skip this. Packaging mistakes are common and cheap to catch early.
Sample package build and deploy

powershell -ExecutionPolicy Bypass -File .\tools\build.ps1
powershell -ExecutionPolicy Bypass -File .\tools\deploy.ps1
Standalone package build and deploy

powershell -ExecutionPolicy Bypass -File .\tools\build.ps1 -SourceDir .\src\packages\iron_archipelago -OutputPath .\dist\iron_archipelago.kyt
powershell -ExecutionPolicy Bypass -File .\tools\deploy.ps1 -PackagePath .\dist\iron_archipelago.kyt
Optional but strongly recommended verification

Get-FileHash .\dist\norwegian_shadow.kyt -Algorithm MD5
Get-FileHash .\dist\iron_archipelago.kyt -Algorithm MD5

Then confirm the deployed package copies match the same hash for the package you actually built, fully restart MNW, and verify that the campaign appears and that each mission can at least load.

5

Start the operator console

The UI is your state dashboard and result drafting surface.
powershell -ExecutionPolicy Bypass -File .\tools\run-dev.ps1

This runs the repo validation path, exports the current UI state snapshot, starts the local server, and opens the browser.

6

Play Mission 1 and capture the result

You now have two valid reporting paths.

Manual Builder Path

  • Open the UI.
  • Use Manual Result Builder.
  • Set mission ID, outcome, elapsed hours, ammo, damage, or destruction.
  • Download the normalized JSON.

Debrief Parser Path

  • Paste MNW debrief text into Debrief Text Parser.
  • Parse the draft.
  • Load it into the manual builder.
  • Correct anything the parser inferred poorly, then export JSON.

The parser can now infer elapsed time, detect common damage or destruction phrases, and map platform names to persistent unit IDs when the runtime snapshot is available.

If the debrief screen hangs on Saving..., stop treating it as a persistence-UI problem. Check Player.log first and inspect mission formations or other snapshot-time objects.

7

Ingest the result and refresh state

This is the handoff from played mission into persistent campaign state.
powershell -ExecutionPolicy Bypass -File .\tools\ingest-and-refresh.ps1 -ResultPath "C:\Path\To\mission1_result.json"

Reload the UI and verify that order of battle, mission history, and generation directives updated.

This external persistence loop is currently authoritative for this repo. It complements MNW's own debrief screens, but it does not depend on any in-game automation bridge.

8

Use the persisted state to shape Mission 2

This is where the AI becomes useful again.
Good follow-up instruction

"Read the updated state and UI snapshot. Generate Mission 2 so it reflects the current campaign condition.
Carry over player damage, readiness, and ammo. If the enemy was destroyed, replace the central threat with an
escalation response. If the enemy escaped, thicken the battlespace and continue the hunt. Keep the campaign graph stable
until this mission saves and unlocks correctly in MNW."
9

Repeat for Missions 2 and 3

Play, report, ingest, refresh, and regenerate.

By the end of Mission 3, you should have:

  • a packaged campaign that loads in game
  • three authored scenarios with escalation
  • mission history in persisted state
  • an order of battle that reflects cumulative results
  • a documented workflow an AI can repeat for future campaigns

Recommended validation order: first prove Mission 1 unlocks Mission 2, then prove Mission 2 saves cleanly, then add or validate Mission 3 progression. That sequence avoided repeated false leads during live testing.

Reporting Mission Results

What to report after each mission

  • mission ID
  • outcome such as success, partial success, failure, or abort
  • elapsed hours
  • weapons expended
  • damage taken by persistent units
  • destroyed units that should not return later

Why this matters

  • damage modules degrade or repair units over time
  • ammo modules prevent infinite reloads between missions
  • mission history drives campaign narrative continuity
  • future scenario generation can read this state and branch intelligently
Practical reporting loop

1. Finish or quit the mission in MNW.
2. Read the debrief / after-action information.
3. Build or parse a normalized result JSON.
4. Ingest the result JSON with tools/ingest-and-refresh.ps1.
5. Reload the UI and confirm the campaign state changed.
6. Ask your AI tool to use that updated state when authoring the next scenario.

What Good Looks Like

Minimum successful outcome

  • The campaign appears in MNW.
  • All three scenarios can be opened and started.
  • You can report each mission through the UI and ingest the result locally.
  • The UI reflects cumulative state after each mission.
  • Your AI tool can read that state and generate the next scenario with continuity.

This guide is deliberately local-first. It assumes the user owns their own MNW install, their own AI tool, and their own campaign data. The repo provides the structure, scripts, persistence contracts, and UI surface needed to make that workflow repeatable.
